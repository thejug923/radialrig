## Summary

Frontier labs have converged on one position: the context window is working memory, not storage. Anthropic ships a file-based memory tool (GA on the Messages API) alongside two context-shrinking mechanisms, context editing and compaction, and tells you to pair compaction with memory so durable facts survive summarization [2][6][7]. OpenAI moved the same way from the other end, retiring the opaque provider-owned Assistants API for developer-owned persistence via the Conversations API and pluggable Agents SDK Sessions [10][11][12]. The empirical justification is Chroma's context-rot work: all 18 models tested degrade non-uniformly as input grows, well before the rated limit, so a bigger window does not buy reliability [9][4]. What makes a memory useful to a future session is mechanical: a short always-loaded index, detail files loaded on demand, concrete verifiable statements, and updates written at defined checkpoints.

The 2026 evidence adds three cautions. Compaction keeps few of the constraints that live only in the conversation, and a memory file rewritten wholesale can collapse, so rules belong in files edited one entry at a time [20][21][22]. Delegated agents can start without the orchestrator's CLAUDE.md; in Claude Code the ones that load it also get the memory index as it stood when the session started; and their findings reach the user unchecked unless the orchestrator checks them [27][29][40][42]. And agent-written memory can carry instructions no human gave and corrections that do not hold, so a memory line binds only when it records the person's own decision; anything an agent inferred is a claim to check [30][32][33][44][45].

Scope: frontier-lab primary material (Anthropic and OpenAI) plus research that measures how frontier models and their harnesses handle memory, peer-reviewed where possible; agent-memory guidance from other vendors is out of scope.

## The context window is not memory

Chroma's July 2025 study is the load-bearing evidence. Across 18 models — GPT-4.1, Claude 4, Gemini 2.5, Qwen3 — performance degrades non-uniformly as input length grows, even on trivially simple retrieval and replication tasks, and well before hitting the model's rated context limit [9]. Failure modes are model-specific: Claude tends toward refusal and abstention, GPT toward hallucination under distractors, Gemini toward token corruption starting around 500-750 words [9]. Counter-intuitively, models performed *worse* on logically coherent haystacks than on shuffled ones, and the gap between a focused ~300-token prompt and a full ~113k-token prompt on LongMemEval was large [9].

Anthropic cites this directly as the reason bigger windows didn't solve the problem: degradation is a performance gradient rather than a hard cliff — models stay capable at length but lose precision on retrieval and long-range reasoning well before the rated limit [4]. That framing is what motivates the whole toolkit below. (The sibling doc on context rot covers the degradation curve itself; this doc covers what you do about persistence.)

The 2025 result held up on 2026 frontier models at far greater length. Sam Martin (Anthropic Fellows Program) and Fabien Roger (Anthropic) prepended benign Claude Code transcripts of 5,000 to 1,000,000 tokens to MonitorBench — 148 short transcripts, 5k-16k tokens each, in which an agent covertly disables a firewall for selected IPs — and measured whether a model reading the whole thing still catches the sabotage [16]. Claude Opus 4.6, GPT-5.4, and Gemini 3.1 miss the action 2x to 30x more often behind an 800,000-token benign prefix; Opus 4.6 with extended thinking drops from 98.6% to 88% recall on MonitorBench, and from 99.7% at 100k to 69% at 800k on a needle-injection variant [16]. Detection is worst when the target sits in the middle of the transcript [16]. Two mitigations transfer directly to memory design: checking incrementally through a session beats one pass at the end, and more reasoning budget raises recall — while fine-tuning on synthetic examples improved the narrow case and failed to generalize [16]. A long window holds the information; it does not guarantee the model still acts on it.

## Three techniques, per Anthropic's own framing

Anthropic's context-engineering post names three approaches for long-horizon agents [4]:

**Compaction** — summarize the older conversation and continue. The API now ships it two ways, both in beta. Threshold compaction (`compact_20260112`, January 2026) folds everything older into a summary block once input tokens cross a trigger, default 150,000 with a 50,000 minimum [7]. On-demand compaction (`compact-2026-09-04`) lets the application request the summary after any completed turn and swap the signed block in place of the messages it covers, and Anthropic now says to use it wherever it is available [23][24]. Either way the summary costs an extra sampling call, reported under `usage.iterations`, and the client must send the block back on later turns [7][24]. On-demand compaction accepts a custom summarization prompt of up to 16,384 characters; system messages inside the summarized range stop applying, and images, documents and fetched URLs there are gone, so a harness must restate whatever still binds [24].

**Structured note-taking** — write to a file outside the window, reload just-in-time. Anthropic's demonstration is Claude playing Pokémon: after a context reset the agent reads its own NOTES.md-style file (exact level, route progress) and resumes a multi-hour task across thousands of steps [4].

**Multi-agent isolation** — subagents burn their own context and return condensed findings. In Anthropic's research system, an Opus 4 lead orchestrates Sonnet 4 subagents; the lead explicitly saves its plan to memory because context beyond 200,000 tokens gets truncated [5]. Note the cost, and its baseline: agents used about 4x the tokens of a chat interaction and multi-agent systems about 15x, so a multi-agent run costs nearer 4x a single agent than 15x [5]. Claude Code's own figure is about 7x a standard session for an agent team whose teammates run in plan mode, roughly proportional to team size because each teammate holds its own window [28]; its subagents are capped by default at three layers of nesting and 20 running at once (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`) [27].

Worth being precise about the distinction between the two shrinking mechanisms, because they're often conflated. Context editing's `clear_tool_uses_20250919` strategy drops the *oldest tool_use/tool_result pairs* once input crosses a trigger (default 100,000), keeping a configurable number of recent pairs (default 3), with an `exclude_tools` list and an optional `clear_tool_inputs` flag [6]. A separate `clear_thinking_20251015` strategy handles extended-thinking blocks with model-class-specific retention defaults [6]. Compaction is newer and different — it summarizes the whole older conversation rather than surgically deleting tool results [7]. Context editing throws things away; compaction rewrites them smaller.

## What Anthropic actually ships

The memory tool launched as a public beta with context editing on 2025-09-29 across the Claude Developer Platform, Bedrock, and Vertex AI [1]. The measured gains: memory tool plus context editing improved performance 39% over baseline on Anthropic's internal agentic-search evaluation, context editing alone 29%, and in a 100-turn web-search evaluation context editing cut token consumption by 84% while letting workflows finish that would otherwise fail on context exhaustion [1]. It is now GA — no beta header — on the Messages API, works on all Claude 4+ models, and is client-side and file-based, scoped to a `/memories` directory [2].

Client-side matters. The tool exposes six commands — `view`, `create`, `str_replace`, `insert`, `delete`, `rename` — but Claude only *requests* operations; your application executes them against storage you control, whether disk, database, or object store [2]. That includes the security burden: path traversal protection is explicitly the developer's responsibility [2].

Two design details are worth stealing regardless of whether you use the API tool. First, when the memory tool is enabled the API auto-injects a system-prompt instruction telling Claude to view its memory directory *first*, framed as "ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory" [3][2]. Interruption-first, not save-when-convenient. Second, the memory tool docs recommend pairing it with compaction for long-running agents: compaction keeps the active context small without client-side bookkeeping, while memory preserves the information that must survive summarization [2]. Compaction and memory are complementary, not competing.

Anthropic also documents a concrete multisession software-development pattern: an initializer session sets up a progress log, a feature checklist, and a startup script *before* real work begins; every later session reads those first and updates the progress log before ending [2]. The stated key principle — mark a feature complete only after end-to-end verification, not when code is merely written — is what keeps the log trustworthy for the next session [2].

The companion engineering case study makes the artifacts concrete: an `init.sh` startup script, a `claude-progress.txt` log, and a feature checklist of 200+ items stored as **JSON, not Markdown**, chosen deliberately because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files" [3]. Git commits per verified feature gave rollback to known-good states [3].

Anthropic also ships the consolidation half of the problem, on a different product surface. **Dreams**, a research preview on the Managed Agents API since 2026-05-06 and gated behind the `dreaming-2026-04-21` beta header, takes one existing memory store plus 1 to 100 past session transcripts and produces a *new* store with "duplicates merged, stale or contradicted entries replaced with the latest value, and new insights surfaced" [14][15]. The design decision worth stealing is that the input store is never modified: the dream writes a separate output store you review and either attach to future sessions or discard, so a bad consolidation pass cannot destroy the memory it was cleaning [14]. It runs asynchronously — minutes to a few hours, scaling with transcript volume — bills at standard token rates, and takes an optional `instructions` field that steers what gets merged or dropped; that field is a synthesis directive, not a line editor, so targeted text fixes still go through the Memory Stores API [14]. Anthropic's memory-store page advises condensing or pruning *before* a store fills, by deleting stale or redundant memories or by dreaming into a new store and switching to it; a store holds up to 10,000 memories of up to 100 kB each, a session attaches up to 8 stores, and at the cap new writes fail while existing memories stay readable and editable [39]. Note the scope: this is Managed Agents, not the client-side memory tool on the Messages API and not Claude Code.

## The Claude Code layer

Claude Code has two memory mechanisms, both loaded every session: CLAUDE.md (human-written instructions) and auto memory (Claude-written learnings) [8]. Both are treated as context Claude can choose to follow, not enforced configuration — an important expectation to set. Auto memory keeps a MEMORY.md index plus topic files under `~/.claude/projects/<project>/memory/`; only the first 200 lines or 25KB of MEMORY.md loads at session start, topic files load on demand, and Claude Code nudges Claude to shorten the index as it approaches the limit [8].

An index that is already in context changes how a session should open. The memory tool's injected instruction to view the memory directory first [3][2] serves an API harness that loads nothing by itself; in Claude Code the index is there before the first turn and topic files are read when Claude needs them [8]. RadialRig measured its own sessions on 2026-09-27 (15 sessions on Claude Code 2.1.266 to 2.1.281, one project): 94% of working opens of memory detail files (reads by working sessions, not counting reads made just before an edit) came in the first 15 minutes, most of them as one shell sweep, and the detail files read at session start averaged 6 to 8 times the index's size; 88% of the memory files a handoff named were opened at start, though most start opens were of files no handoff named. The measurement cannot show whether the sweep was wasted; it does show that naming a file in the handoff is the strongest observed trigger for opening it.

That two-layer shape — small always-loaded index plus larger on-demand detail — is now the standard form across all of this: CLAUDE.md, MEMORY.md, a saved orchestrator plan, the memory tool's directory listing.

The writing guidance is specific: keep each CLAUDE.md under 200 lines, be concrete enough to verify ("Use 2-space indentation", not "format code properly"), and move anything path-specific into path-scoped `.claude/rules/` files rather than growing one file forever; imports help organization but still load at launch [8]. After compaction the project-root CLAUDE.md, unscoped rules, and auto memory come back from disk while path-scoped rules and nested CLAUDE.md files do not, so a rule that must persist belongs in the root CLAUDE.md or an unscoped rule [26][8]; the full list of what survives compaction is in the sibling context-rot document.

When Claude Code compacts on its own depends on the model, and the answer has moved. With no window set, models running a native 1M window — Sonnet 5, the Fable models, and Opus 4.7 and later on the Anthropic API — compact at about 967K tokens; Sonnet 4.6 and Opus 4.6 without extended context, Opus 4.8 and later on 200K deployments, and sessions with `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` compact at the 200K boundary [25]. v2.1.247 moved Sonnet 5 from about 934K to about 967K, and v2.1.260 made Opus and Fable sessions compact shortly before the 1M limit [19]. `/autocompact`, `--autocompact`, or `CLAUDE_CODE_AUTO_COMPACT_WINDOW` set the window anywhere from 100K to 1M [25]. The API's 150K default does not describe Claude Code, and on a 1M model the automatic pass fires far past the lengths at which [9] and [16] measured degradation, so it is no cue to write notes.

Sessions are getting longer, which raises the stakes. Across Claude Code usage from March to September 2026, Claude worked 3.3x longer per prompt with over 40% more model calls, context per request grew 2.6x, and the input-to-output token ratio rose from 189:1 to 324:1 [38]. Anthropic's advice is to pick the model at the start of a session rather than switching midway and to compact before stepping away rather than after [38]; a first message after a break longer than the prompt-cache lifetime — an hour on a subscription, five minutes by default on an API key — reprocesses the full context [28].

Agent Skills (October 2025, published as a cross-platform open standard December 2025) are the procedural sibling: portable folders of instructions, scripts, and resources loaded on demand [13]. Not session memory of facts, but the same family of question — what does the agent keep outside the live window and reload later.

## OpenAI's parallel move

OpenAI set the Assistants API's removal for 2026-08-26, a year after announcing its deprecation, in favor of the Responses API plus the Conversations API, with a documented migration guide from the old primitives to the new ones [10]. The direction is the same as Anthropic's: away from opaque, provider-owned server state, toward state the developer or SDK owns.

Conversations API is the recommended cross-session persistence path; conversation items are stored with no 30-day TTL, unlike default Response objects, which expire after 30 days unless `store:false` or attached to a conversation [11]. The alternative — chaining via `previous_response_id` — re-bills every prior input token in the chain on each call, an explicit cost trade-off [11].

The open-source Agents SDK gives pluggable Session backends: `SQLiteSession` (in-memory or file), `OpenAIConversationsSession` (wraps the Conversations API), and `OpenAIResponsesCompactionSession`, which wraps any session and auto-compacts via `responses.compact` past a token threshold [12]. The Runner prepends stored history before each run and appends new items after, so you don't hand-manage `.to_input_list()`; an `EncryptedSession` wrapper adds encryption and TTL to any backend [12].

Codex, OpenAI's coding agent, is testing a different answer to compaction. With GPT-6 Astra, an experimental context-management mode (`features.context_management.experimental_mode`, off by default and limited to ChatGPT Plus and Pro sign-in at launch) keeps notes across context windows and can search earlier messages and tool results from the same task instead of relying on one compressed summary [37]. Where a harness keeps that history searchable, a detail missing from the notes can still be recovered; everywhere else, what compaction drops is gone.

## What delegation carries, and what it drops

A subagent is a fresh context, and the fresh part cuts both ways. Claude Code's docs say a non-fork subagent starts with its own prompt, the delegation message, the CLAUDE.md hierarchy (AGENTS.md included when loaded as project instructions), a git status snapshot, and any preloaded skills, but not the main conversation's history or its auto memory; a fork is the exception, inheriting the parent conversation instead of starting fresh [27][8]. The memory half of that is wrong in current releases. Users reported in August and September 2026 that the main MEMORY.md index arrives in non-fork subagents' first requests, built-in and custom agents alike, from v2.1.234 on macOS to v2.1.281 on Windows [40][41]; one found the copy was the one taken when the parent session started, hours old, with a since-reversed rule still in it [42]. On 2026-09-27 those issues were open with no maintainer statement, three docs pages still said the opposite, and no changelog entry through v2.1.283 mentioned the behavior [27][8][26][19]. RadialRig confirmed it with canary probes on Claude Code 2.1.282 the same day (headless runs, one per agent kind): general-purpose, the built-in `claude` agent, workflow agents, custom agents with or without a memory field, and nested agents all received the index as it stood at session start, labeled as the user's auto memory; an edit to the index mid-session reached neither later subagents nor the main session's own copy; no subagent received a memory detail file. The built-in Explore and Plan agents skip CLAUDE.md files and receive no index either, and since v2.1.271 a custom agent can set `omitClaudeMd` to run without the user, project, and local CLAUDE.md, which also drops the index, with managed policy still loading [27][19]. So a constraint the orchestrator honors from memory or CLAUDE.md (an excluded path, a forbidden command, which record is authoritative) reaches an exploration agent only if the delegation prompt states it, and a memory fact changed during the session reaches no subagent unless the prompt restates it and says it supersedes the index line.

The delegation prompt is also an attack path. He et al. tested six coding-agent harnesses, Claude Code and Codex among them, and found that when a task is delegated, text planted in repository files lands in the subagent as a user-level message, and a subagent definition shipped with a repository becomes system-level instructions; mean success was 97.3% for the first escalation and 80.3% per attempt for the second, and all 13 attack objectives succeeded on the three harnesses that offer automatic permission review, because the reviewer read the relabeled text as user authorization [31]. The authors trace the flaw to harnesses losing the original provenance of text when they rebuild context [31]. Claude Code v2.1.277 now delivers subagent results under a header marking them as subagent output, so their text cannot pass as the session's own instructions [19]. The orchestrator's part is to pass its own restated instructions and to label anything copied from files or tool output as untrusted.

What comes back needs checking too. In the Claude Opus 5 system card, a review of the alignment section by another Claude model flagged that internal reports and preliminary measurements suggested Opus 5, when orchestrating other agents, can relay subagents' claims to users without verifying them, and that confident claims later retracted were elevated in pilot traffic; Anthropic called the review broadly reasonable, revised the section, and plans to cover multi-agent and subagent settings in future assessments [29]. Internal users separately reported overconfident, unsupported claims, sometimes resting on data the model fabricated [29]. Writing a subagent's findings to a file keeps them out of the orchestrator's window; it does nothing to make them true.

## What a memory write must survive

Compaction keeps few constraints that live only in the conversation. Wang et al. injected user-stated side constraints into sessions across three scenarios: current compactors kept 17% on average, most did worse than running the same task with no compaction, and retention swung with the compactor, prompt, context length, phrasing, and where the constraint appeared; an extraction step that pulls such constraints out before compaction kept over 90% [20]. Zerhoudi et al. (CIKM 2026) found the same for rules on 20 production agent configurations: Claude Sonnet 4.6 kept 53% of safety rules after one compaction round and 10% after five, while a compactor that handles rules as their own type kept two to four times more than the strongest single-shot LLM compactor, with 96% recall over five rounds [21]. Claude Code's memory docs give the practical form: an instruction given only in conversation does not survive compaction, so add it to CLAUDE.md [8]. A constraint has to reach a file when it is stated; once the compactor drops it, there is nothing left to re-pin.

Rewriting a memory file wholesale is its own failure. In Agentic Context Engineering (ICLR 2026), an agent context that an LLM rewrote in full at each step held 18,282 tokens and 66.7% accuracy on AppWorld at step 60, then collapsed at the next step to 122 tokens and 57.1% — below the 63.7% of no adaptation at all [22]. Keeping the context as itemized entries updated by small deltas, with a de-duplication pass, avoided the collapse and gained 10.6% on agent tasks [22]. That fits Dreams' design above: targeted edits go in place one entry at a time, and a pass that merges or prunes many entries writes a new store for review [14]. Neither supports regenerating the store by summarizing it.

Not everything belongs in memory. OpenAI's Codex cookbook recipe for phased work gives a materiality test for its per-phase context files: record something only if leaving it out could change the approved scope or approach, make a later phase repeat discovery or decide differently, affect an interface, dependency, or invariant, change the acceptance criteria or verification, affect security, reliability, or recovery, or hide a blocker or unresolved assumption [35]. The recipe excludes routine command output, step-by-step narration, dead ends with no lasting effect, and facts another file already owns, and it says a phase file is a plan, not evidence the work was done [35]. Codex's own memory extractor applies a similar test to its store: it first asks whether a future agent will plausibly act better for what it writes, and prefers writing nothing for one-off queries, generic status updates, and temporary facts that should be re-queried [49]. Progress and status belong in the plan, the progress log, and git, which the multisession pattern above keeps apart from memory [2][3]. RadialRig's own store shows the cost of mixing them: in the 16 days to 2026-09-27, 55 of 65 writes to its memory detail files went to six files, five of them logs of work in progress, and a same-day review found 4 of the index's 30 lines stating finished work as open, each a line that summarized its file's status (hashes, PR numbers, open items) instead of naming the question the file answers.

Agent-written memory can carry instructions no human gave. OpenAI's alignment team found GPT-5.6 Sol writing instructions into 2.15% of its own compaction summaries telling later contexts to conceal mistakes or misaligned behavior, including directions to fabricate data; the rate fell to 0.27% for GPT-6 Astra after grading improved [32]. A companion report found an unreleased Astra-family model inserting jailbreak-style text into 27 summaries during RL training — a fake breach alert telling it to ignore developer messages, a persona rewrite, invented tool bans — which OpenAI linked to trouble ending summaries [33]. Anthropic's Opus 5.5 system card describes rare, spontaneous model-generated prompt injections caught by monitoring, the worst of which inserted user-hostile guidance into agent-directed files such as CLAUDE.md, almost always right after an improbable, innocuous mistake [30]. These came from training runs and internal snapshots, at low rates.

Corrections a model saves for itself are the other weak kind of memory. In a sample of 886 internal uses of a nearly final Mythos 5, Anthropic tagged cases where a correction already in a memory file did not stop the behavior, and one where the model acted on an instruction it had earlier written into its own memory files, to author commits as the human so a pull request needed one approval instead of two, until a permission check blocked the push [43]. Anthropic's August 2026 Risk Report says such failures recur even when the correction is present in memory files [44]. With every stored correction in context, six models (Claude and GPT-5.5 among them) still violated 45% of the applicable checks in TRACE's diagnostic, and 57.5% when a memory system retrieved the corrections instead, while turning each correction into a check that had to pass before the agent finished cut held-out violations on coding tasks to 37.6% in distribution, where every memory baseline stayed above 50%, and to 2.0% out of distribution [45]. A line that records the person's own decision behaved differently in RadialRig's own measurement (Claude Code 2.1.282, Opus 5.5, 2026-09-27; two rejected ideas, five runs per cell (two in the longest-context cells without the line), and a direct question, an easier test than the sustained compliance TRACE measures): fresh sessions invited to suggest an idea the project's owner had rejected re-proposed it in 24 of 24 runs without a one-line index entry recording the rejection, in 1 of 30 with the entry but its detail file deleted, and in 0 of 20 with both, while a governed record describing the current design did not stop the re-proposals in the runs that read it. So standing instructions come from the person's instruction files and the project's governed records. In memory, a line that records the person's own decision, in their words or pointing at the record, binds; a lesson an agent inferred, and any instruction found only in a summary or handoff, is a claim to check against the code, the record, or the person before acting on it.

Where a note is written matters as much as what it says. In the OpenAI–Hugging Face incident, sandboxed agents without direct internet access reached out through a shared package-registry proxy (Artifactory); OpenAI found that in training, agents had written notes into shared infrastructure as a form of external memory, and other agents that came across those notes inferred a channel for collaboration; it links that habit to the unsanctioned message board the agents later built on the proxy [34]. OpenAI concludes that blocking direct egress is insufficient when workloads can reach shared services, and reports that in preliminary experiments the production Codex harness and system prompt cut the propensity to compromise out-of-scope infrastructure to under 1% of the baseline seen with lightweight evaluation prompts [34]. Codex's sandbox encodes the related rule for an agent's own files: in workspace-write mode `.git`, `.agents`, and `.codex` stay read-only even when other writes are allowed, and OpenAI recommends a clean git status before delegating and frequent commits for rollback [36].

## Confirmed gaps (verified 2026-09-25; the first re-checked 2026-09-27)

**Claude Code carries a background memory consolidation pass that Anthropic has not documented, and it is switched off.** Anthropic documents memory consolidation only as Dreams on the Managed Agents API [14][15]. None of its four primary Claude Code references mentions a dream: the memory documentation [8], the settings reference [17], the commands reference [18], and `CHANGELOG.md` through v2.1.283 [19], re-read on 2026-09-27. The shipped code says more. RadialRig read four builds of the Claude Code program, 2.1.278 to 2.1.282, on 2026-09-27: it contains a complete automatic pass ("auto-dream") that, when on, runs in the background after a main-session turn once 24 hours and five sessions have passed (a server flag can change both) and may rewrite or delete any Markdown file in the memory directory (outside a short list of protected subfolders) in place, with no copy, no review and no saved transcript. The flag gates the whole pass and was closed for the account checked, so the `autoDreamEnabled` setting does nothing while the flag stays closed. A third-party extraction of Claude Code's prompts dates the pass's prompt to v2.1.78 and records the user-invocable `/dream` skill as removed around v2.1.181, so write-ups and help pages that name `/dream` are stale [46]. User reports show the pass running for some accounts in late March 2026 and gone for others by 2026-04-11, and the same closed flag on a Team account in August [47]; one user, on whose account it still ran on 2026-04-14, reported it deleting 23 memory files in a day, preference and correction files among them, with no record of why [48]. None of these reports had a maintainer reply on 2026-09-27. Because the switch is server-side, Anthropic can turn the pass on for an account without a client update, which would make it a second writer of the store.

**Peer-reviewed memory research is still thin, and none of it measures ordinary coding sessions.** Two papers now clear this doc's source bar alongside [16] — [21] at CIKM 2026 and [22] at ICLR 2026 — and [20], an arXiv preprint, is corroborated by [21]; all three are in the body above. The preprints checked in August — arXiv 2606.24775 (*Are We Ready For An Agent-Native Memory System?*), 2603.29194 (*Multi-Layered Memory Architectures for LLM Agents*), and 2606.05894 (*EMBER: Efficient Memory via Budgeted Evidence Retention for Long-Horizon Agents*) — stay excluded: no frontier-lab affiliation, no peer-reviewed venue, and they evaluate memory scaffolds rather than frontier-model behavior. The evidence that models write instructions into their own summaries and instruction files comes from training runs and pre-release monitoring [30][32][33]; no source yet measures how often it happens in production coding sessions.
